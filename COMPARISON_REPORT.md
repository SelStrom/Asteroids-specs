## 2. Архитектурное сравнение

### 2.1 Общая архитектура — **совпадение ~70%**

Обе реализации следуют **одной и той же гибридной архитектуре:**


| Слой                       | Паттерн                                               | Совпадает?                   |
| -------------------------- | ----------------------------------------------------- | ---------------------------- |
| Модель (игровая логика)    | Custom ECS-like: Entity + Component + System          | **Да** — одинаковая иерархия |
| Представление (UI/визуалы) | MVVM через com.shtl.mvvm                              | **Да** — один фреймворк      |
| Реестр сущностей           | EntitiesCatalog (фабрика + привязки)                  | **Да** — та же роль          |
| Входные данные             | Unity Input System + PlayerInput-обёртка              | **Да** — одна схема          |
| Visitor для регистрации    | IGroupVisitor + GroupCreator                          | **Да** — один паттерн        |
| Точка входа                | ApplicationEntry (MonoBehaviour) → Application → Game | **Да** — та же цепочка       |


**Вывод:** AI корректно воспроизвёл высокоуровневую архитектуру. Namespace `SelStrom.Asteroids`, папочная структура (`Application/`, `Model/`, `View/`, `Configs/`, `Input/`, `Utils/`), и паттерны проектирования воспроизведены верно.

### 2.2 Ключевые архитектурные расхождения


| Аспект                   | Оригинал                                                      | Восстановленная                                                                    |
| ------------------------ | ------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **Сигнатура UpdateNode** | `UpdateNode(TNode node, float dt)` — только компонент         | `UpdateNode(IGameEntityModel entity, TNode node, float dt)` — сущность + компонент |
| **Состав System-нод**    | Tuple из нескольких компонентов `(Move, Gun, ShootTo)`        | Одиночные компоненты + type-check entity в runtime                                 |
| **Управление вращением** | `Quaternion` + отдельный `ObservableValue<Vector2> Rotation`  | Тригонометрия `Atan2` + direction вектор из `MoveComponent`                        |
| **Направление тяги**     | По направлению носа корабля (facing) — классический Asteroids | По текущему вектору движения — нестандартный подход                                |
| **AI НЛО**               | Предиктивный перехват (упреждающее прицеливание)              | Простое преследование (direction = target − pos)                                   |
| **Подсчёт боеприпасов**  | Обратный отсчёт (Max → 0)                                     | Прямой отсчёт (0 → Max)                                                            |
| **Отслеживание пула**    | В ViewFactory + BaseVisual с Dispose()                        | В IEntityView через PrefabInstanceId                                               |
| **ReactiveValue**        | Единообразно `ReactiveValue<T>`                               | Смешанно `ObservableValue<T>` / `ReactiveValue<T>`                                 |

## 7. Качественный анализ ключевых расхождений

### 7.1 Что AI воспроизвёл верно

- **Архитектурный каркас:** ECS-like Model с Systems/Components/Entities, MVVM View, Application как фасад
- **Зависимости:** Точное совпадение пакетов и их версий
- **Конфигурационный слой:** ScriptableObject-иерархия воспроизведена почти 1:1
- **Visitor-паттерн:** IGroupVisitor + GroupCreator — тот же подход
- **Имена классов и файлов:** ~90% совпадение именования
- **Фреймворк MVVM:** Тот же com.shtl.mvvm, те же базовые классы

### 7.2 Что AI реализовал иначе (корректно, но по-другому)

- **Декомпозиция экранов:** 5 отдельных экранов vs 1 мега-контроллер — аргумент за рекон. (чище SRP)
- **Волновая система:** Оригинал не имеет волн — рекон. добавил из спецификаций классического Asteroids
- **Жизни/Respawn:** Оригинал — instant death; рекон. — полный lives-система
- **Аудио:** Отсутствует в оригинале, полноценно в рекон.
- **Leaderboard:** 6 файлов с interfaces vs 1 файл async/await — trade-off testability vs simplicity

### 7.3 Что AI реализовал некорректно / с потерей качества

- **Thrust по вектору движения** вместо facing direction — нарушает каноничную физику Asteroids
- **Отсутствие предиктивного AI** у UFO — значительное упрощение поведения
- **Лазер — заглушка** (`Debug.Log`) — критическая недоработка
- **Отсутствие `ReceiveScore`** в Model — скоринг вынесен в Game, нарушая инкапсуляцию
- **Смешение ObservableValue/ReactiveValue** — стилистическая неконсистентность

## 9. Выводы

### 9.1 Успехи AI-реконструкции

1. **Архитектурная верность (70%)** — AI корректно восстановил гибридную архитектуру ECS-like + MVVM, что является сложной и нетривиальной комбинацией
2. **Структурная организация (85%)** — файловая иерархия, namespaces, зависимости воспроизведены точно
3. **Конфигурационный слой (85%)** — ScriptableObject-иерархия почти идентична
4. **Расширение функциональности** — AI добавил канонические механики Asteroids (волны, жизни, аудио), которые улучшают игровой опыт
5. **Пакетные зависимости (100%)** — точное совпадение версий

### 9.2 Проблемы AI-реконструкции

1. **Алгоритмическая точность (35%)** — физика, AI, управление состоянием существенно отличаются
2. **Лазер — заглушка** — критический пробел в функциональности
3. **Неканоничная физика тяги** — thrust по движению вместо facing нарушает игровой канон
4. **Упрощение AI** — потеря предиктивного перехвата UFO
5. **Стилистическая неконсистентность** — смешение ObservableValue/ReactiveValue, «толстые» визуалы

### 9.3 Общая оценка

AI способен восстановить **архитектурный каркас** с высокой точностью (~~70-85%), но **конкретная реализация алгоритмов** существенно расходится (~~35%). Это ожидаемо: спецификации описывают *что* должна делать система, но не *как* именно. Для продакшн-использования потребуется код-ревью и доработка алгоритмического слоя.

**Рекомендация:** AI-реконструкция из спецификаций — эффективный инструмент для быстрого прототипирования и восстановления проектной структуры. Для полного соответствия оригиналу необходимы дополнительные спецификации на уровне алгоритмов или прямое copy-paste ключевых формул.
